## 🔴 C1. Молчаливая потеря первого turn'а сессии (`_update_file_meta` + falsy 0)

**Где:** `src/deja/indexer.py:179` (`offset = completed_offset if completed_offset else stat.st_size`), вызов из `indexer.py:129-131`.

**Сценарий:** `deja index` запускается (cron / вручную), когда сессия только началась — в файле есть user-сообщение, но assistant ещё не ответил.

1. `parse_jsonl_file` не выдаёт ни одного turn'а (нет пары) → `indexed_any=False`.
2. `_update_file_meta(conn, path, offset)` вызывается с `offset=0` → **0 falsy** → берётся `stat.st_size`, т.е. файл помечен проиндексированным **до конца, включая непроиндексированный user**.
3. Следующий запуск: incremental, resume с offset за user-сообщением → первым читается assistant → `pending_user is None` → turn выброшен.
4. `last_offset` навсегда застревает перед этим assistant. Первый turn сессии (вопрос + ответ) потерян до `--reindex`.

Тест `test_dangling_user_not_lost` это не ловит — там перед dangling user есть полный turn (`indexed_any=True`, offset правильный).

**Фикс (2 строки):**
```python
# indexer.py:179
offset = completed_offset if completed_offset is not None else stat.st_size
```
При `offset=0` сохранится 0 → следующий запуск перечитает файл с начала и подберёт turn. Файлы без turn'ов и без роста не зациклятся (отсечёт `mtime==`/`size==` → `False`).

**Тест:** файл только с user-строкой → `index_file` → дописать assistant → `index_file` → turn должен появиться.

## 🟠 M1. Секреты утекают в индекс: усечение и чанкинг происходят ДО redact

**Где:** усечение — `src/deja/parser.py:36` (`raw[:TOOL_RESULT_MAX]`) и `parser.py:93`; чанкинг — `chunker.py`; redact — только в `indexer.py:114-116`, после обоих.

Два конкретных вектора утечки:

1. **Усечённый приватный ключ.** Tool result от `cat ~/.ssh/id_rsa` (~2.5KB) усекается до 2000 символов → маркер `-----END ... PRIVATE KEY-----` отрезан → паттерн `secrets.py:15` (требует BEGIN **и** END) не срабатывает → **~1960 символов приватного ключа лежат в `tool_result_text` открытым текстом** и отдаются через MCP `search`.

re.compile(r'-----BEGIN (?:RSA |EC |DSA |OPENSSH )?PRIVATE KEY-----[\s\S]+')

## 🟠 M2. `secrets.py` не ловит «голые» токены — главный кейс tool result'ов

**Где:** `src/deja/secrets.py:5-40`.

Все паттерны (кроме AWS/GitHub/GitLab/Slack) требуют контекст присваивания (`key = ...`, `Bearer ...`). Но самые частые утечки в сессиях Claude Code — **вывод инструментов**: `env`, `cat .env`, Read конфигов, где токен стоит без присваивания или в неизвестном формате ключа. Не редактируются:

- `sk-ant-...` (Anthropic — для инструмента про Claude Code это кейс №1), `sk-proj-...` standalone (OpenAI)
- `dop_v1_...` (DigitalOcean — реально используется в твоей работе), `figd_` (Figma), `npm_`, `pypi-AgEIcHlwaS5vcmc...` (PyPI — сам проект публикуется на PyPI!)
- standalone JWT `eyJ...{20,}\.eyJ...`, `AIza...` (Google), `sk_live_`/`rk_live_` (Stripe), Telegram bot `\d{8,10}:AA[A-Za-z0-9_-]{33}`
- AWS **Secret** Access Key (40 base64) — закрыт только Access Key ID

**Фикс:** добавить блок известных префиксных форматов (дёшево, без false positives):
```python
re.compile(r'\bsk-(?:ant|proj)-[A-Za-z0-9_\-]{20,}'),
re.compile(r'\b(?:dop_v1_|figd_|npm_|pypi-AgEIcHlwaS5vcmc)[A-Za-z0-9_\-]{15,}'),
re.compile(r'\beyJ[A-Za-z0-9_\-]{10,}\.eyJ[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]+'),
re.compile(r'\bAIza[0-9A-Za-z_\-]{35}'),
re.compile(r'\b[rs]k_live_[A-Za-z0-9]{20,}'),
re.compile(r'\b\d{8,10}:AA[A-Za-z0-9_\-]{33}'),
```
Дальний прицел: entropy-based детектор (как detect-secrets) вторым проходом по tool_result_text.

## 🟠 M3. `schema_version` никогда не обновляется после миграции — реиндекс зациклится на v0.4+

**Где:** `src/deja/cli.py:63-69` (wipe), `db.py:73-77` (`INSERT OR IGNORE`).

При будущем бампе `SCHEMA_VERSION` (1→2): `cmd_index` видит mismatch, вайпит данные, переиндексирует — но `meta.schema_version` остаётся «1», потому что `init_db` пишет meta через `INSERT OR IGNORE`, а wipe-ветка meta не трогает. Итог: **каждый** `deja index` делает полный реиндекс (30-40 мин), а `deja serve` вечно отвечает «schema mismatch».

Латентный, но гарантированно выстрелит при первой же миграции схемы (а она понадобится для #13 parent-child и для e5-префиксов из M6).

**Фикс:** в wipe-ветке `cli.py:69`:
```python
conn.execute("INSERT OR REPLACE INTO meta (key, value) VALUES ('schema_version', ?)", (str(SCHEMA_VERSION),))
```
Туда же: `DELETE FROM chunks_vec` не поможет при смене размерности эмбеддинга — виртуальную таблицу `float[384]` надо DROP/CREATE при смене модели.

## 🟠 M4. `gc_orphans` удаляет живые чанки при том же session_id под другим путём

**Где:** `src/deja/indexer.py:186-194` + `_delete_file_chunks` (49-56) — удаление по `session_id`, выведенному из имени файла.

Если один и тот же jsonl оказался в двух project-директориях (перенос проекта, ручное копирование, бэкап): новый путь индексируется, старый путь становится orphan → `gc_orphans` удаляет чанки **по session_id**, т.е. и только что проиндексированные. При этом `indexed_files` для нового пути говорит «всё проиндексировано» → сессия молча исчезает из индекса до `--reindex`.

**Фикс:** перед удалением проверять, что session_id не принадлежит живому пути:
```python
known_sessions = {os.path.splitext(os.path.basename(p))[0] for p in known_paths}
if path not in known_paths and session_id not in known_sessions:
    _delete_file_chunks(...)
```
(удаление записи из `indexed_files` оставить безусловным).

## 🟠 M5. Фильтры project/date применяются ПОСЛЕ retrieval — ложные пустые результаты

**Где:** `src/deja/search.py:118-132`: k=100, RRF, потом `[r for r in merged if r["project_path"] == project]`.

При 65+ проектах в индексе чанки нужного проекта легко не попадают в глобальный топ-100 → MCP `search(project=...)` возвращает пусто/мусор, хотя релевантные чанки в индексе есть. Для пользователя это выглядит как «deja не помнит» — подрыв доверия к инструменту.

**Фикс по нарастающей:**
1. Быстро: FTS-ветку фильтровать в SQL (`JOIN chunks ... WHERE chunks_fts MATCH ? AND c.project_path = ?`) — keyword-поиск по проекту станет точным.
2. Правильно: project_path как metadata-колонка в `chunks_vec` (sqlite-vec 0.1.6+ умеет `WHERE` по metadata в KNN) — требует schema v2 (см. M3!).
3. Паллиатив: при фильтрах поднимать k до 500-1000 (vec KNN на 27k векторах это переживёт).

## 🟠 M6. Отсутствуют префиксы `query:` / `passage:` для e5-модели — недобор качества поиска

**Где:** `indexer.py:107-111` (эмбеддинг документов), `search.py:18` (эмбеддинг запроса).

`multilingual-e5-small` обучена с обязательными префиксами: карточка модели intfloat прямо говорит, что без `query: `/`passage: ` качество retrieval деградирует. M3). **Проверяется имеющимся `deja eval`** на golden_pairs до/после — идеальный кейс для вашего eval-харнесса. Ожидаемо MRR вырастет; если нет — откатить, ничего не потеряно.

## Ветка `feat/codex-parser` (8 коммитов, не смержена)

Реализует #8: parser registry (`parsers/base.py` Protocol + `registry.py`), Codex-парсер,
колонка `source` в chunks, `--source` в CLI/MCP, SCHEMA_VERSION 1→2. Архитектура расширения
правильная — ровно та, что предложена выше для #8. Но мерджить в текущем виде нельзя:

### 🔴 B1. Мердж ломает все существующие индексы (init_db падает, миграции нет)

Старый index.db: таблица `chunks` без колонки `source`, meta `schema_version=1`.
На коде ветки `deja index` → `init_db`: `CREATE TABLE IF NOT EXISTS` не добавляет колонку,
затем `CREATE INDEX idx_chunks_source ON chunks(source)` → **OperationalError: no such column** —
крэш до проверки версии, wipe-ветка в `cli.py:63` недостижима. `deja serve`: schema mismatch
(1 != 2) → мёртвый сервер. Пользователь застревает до ручного удаления index.db.

И даже если бы init_db выжил — выстреливает M3: wipe не обновляет `schema_version`
(INSERT OR IGNORE), вечный полный реиндекс + вечно мёртвый serve.

**Фикс:** миграция в `init_db` ДО создания индексов: читать meta-версию; если меньше текущей —
`DROP TABLE` chunks/chunks_vec/chunks_fts/indexed_files, пересоздать DDL,
`INSERT OR REPLACE schema_version`. Это закрывает и M3. Плюс тест «открыть v1-базу кодом v2».

### 🔴 B2. `deja index --source codex` уничтожает claude-code индекс

`cli.py:85`: `gc_orphans(conn, known_paths)` вызывается безусловно, а `known_paths`
собирается только из выбранных источников. При `--source codex` все claude-code пути
становятся «orphans» → `_delete_file_chunks` сносит все их чанки. И наоборот.

**Фикс:** при `args.source != "all"` пропускать gc, либо добавить `source` в `indexed_files`
и чистить только внутри выбранного источника (правильнее — заодно решает M4 точнее).

### 🟠 B3. Последний turn живой Codex-сессии замораживается недоиндексированным

`parsers/codex.py`: при EOF частичный turn yield'ится с `completed_offset = f.tell()` (EOF).
Если сессия живая и assistant ещё пишет — offset уезжает за turn, дописанные части никогда
не индексируются (resume начнётся после EOF, а `message_index` уже занят).
Переменная `pending_user_line_start` (строки 108, 149) присвоена и **ни разу не прочитана** —
видимо, исходный замысел был отдавать offset начала turn'а, но тогда resume создаст дубликат
(message_index = MAX+1 вместо апдейта). Нужно парное решение: EOF-yield с offset'ом начала
turn'а + resume-семантика «re-upsert последнего message_index», либо не yield'ить
частичный turn вовсе (тогда завершённые сессии теряют финальный turn — хуже).

## Что хорошо (честно)

- Crash-safe инкрементальность: commit после каждого батча с offset'ом, детект усечения файла, resume — продумано и протестировано.
- `fts5_escape` корректен (токен-кавычки с удвоением), fallback на OperationalError.
- WAL + busy_timeout + read-only коннект в сервере: индексер и сервер сосуществуют без блокировок.
- Lazy model load с double-checked locking + `asyncio.to_thread` — MCP стартует мгновенно и не блокирует event loop.
- Тесты — настоящие регрессионные (реальная модель, реальный SQLite), не мок-театр.
- CI-матрица 2 OS × 2 Python с кэшем модели, релиз через trusted publishing — образцово для проекта такого размера.
